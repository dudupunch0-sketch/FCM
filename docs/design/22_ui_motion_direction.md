# FCM UI·캐릭터·카드 연출 설계안

작성: 2026-09-12. 상태: 검토용 제안. 현재 결정 SSOT와 캐릭터 최종 승인 상태를 변경하지 않는다.

후속 결정(2026-09-12): 사용자가 2D 방향을 선택했다. 캐릭터 제작은 [23번 문서](23_2d_character_direction.md)를 우선한다. 아래 도트 표현과 8절 Blender 제작 경로는 초기 제안의 기록이며, 현재 권장 경로는 직접 그린 2D 원화와 프레임 애니메이션이다. UI 반응·카드 편집·판정과 연출의 분리 원칙은 유지한다.

## 1. 방향: 날카로운 스포츠 그래픽과 짧고 묵직한 복싱

생각할 시간은 충분히, 선택 반응은 즉시, 타격은 짧고 선명하게 만든다. 어두운 링 위의 도트 선수와 라임색 콤보 트랙을 시각 중심으로 삼는다. 선택한 카드의 강조색이 배치 슬롯, 재생 위치, 접촉 효과로 이어지는 것이 공통 연출 문법이다.

사용 맥락은 현재 구현에 맞춰 세로 모바일 우선으로 가정한다. 계획에 제한 시간을 추가하지 않는다. 기본 2배 재생, 다음 계획 자동 복귀, 배치 유지, 8칸 시간축을 유지한다. 카드 선택은 기술 배치이며 무작위 드로우나 카드 소모 연출을 도입하지 않는다.

외형은 `../art/reference/link/README.md`와 로컬 이미지 4장을 확인했다. 현재 플레이어 아틀라스도 열어 확인했다. 날렵한 실루엣과 큰 헤어 덩어리를 유지하며, 이번 제안은 새로운 얼굴·복장 승인이나 3D 전환을 포함하지 않는다.

참고할 제품과 적용 범위:

- [Fights in Tight Spaces](https://store.steampowered.com/app/1265820/Fights_in_Tight_Spaces/): 카드 전술과 애니메이션 전투를 결합한다. 우리 게임에는 선택과 결과 동작의 대응을 명료하게 만드는 원칙을 적용한다.
- [Neon White](https://annapurnainteractive.com/ja/games/neon-white): 빠른 액션의 비교 대상으로 삼는다. 카드가 행동을 촉발하는 속도감을 참고하되, 우리 계획 단계의 숙고 시간은 유지한다.

위 적용 내용은 설계자의 제안이다. 해당 게임의 정확한 모션 시간이나 UI 규격을 추출한 것은 아니다.

## 2. 현재 구현에서 출발할 지점

- `dist/index.html`: 선수 상태 → 경기장 → 상대 정보 → 내 콤보 → 카드 → 실행 구조가 이미 있다.
- `dist/style.css`: 남색 바탕, 라임·청록·황색의 의미 구분, 3열 2행 카드가 있다. 카드별 선택·안착 연출은 아직 정의되어 있지 않다.
- `dist/app.js`: 기본 `speed=2`. 편집 때 카드·타임라인 DOM을 재생성하므로 효과 지속과 키보드 포커스를 보존할 필요가 있다.
- `dist/motion.js`: 기본 1칸 760ms를 속도로 나눈다. 2배에서 8칸 약 3.04초이며 정지 연출은 별도다. 강타 정지는 20ms, 카운터는 32.5ms가 된다.
- `dist/pixel-motion.js`: 훅·크로스·강타의 접촉 자세가 공유된다. 준비·회수의 연속 프레임이 부족하다.
- `dist/ring-pixel.js`: 고정 위치 접촉 효과와 전신 상하 흔들림이 있다. 펀치별 접촉점과 지지발 고정을 세밀하게 설계할 여지가 있다.

위는 코드와 원본 아틀라스 확인 결과다. 실제 플레이 화면의 체감 속도와 성능은 아직 검증하지 않았다. 오래된 개발 체크포인트의 '구현 없음' 기록보다 현재 실행 파일을 근거로 삼는다.

## 3. 화면 구성과 시각 규격

```text
선수 이름 / 기력 / 부위별 상태       메뉴
┌──────────────────────────────┐
│        두 선수의 전신          │
│      접촉점 중심의 짧은 효과     │
└──────────────────────────────┘
상대 정보   [확정][?][추정] … 8칸
내 콤보     [동작의 시간 점유] … 8칸
예상 기력 / 편집 안내 / 되돌리기
공격 · 수비 · 전술
[기술][기술][기술]
[기술][기술][기술]
짧은 피드백                 콤보 실행 ▶
```

- 배경 `#101923`, 패널 `#182533`, 글자 `#EDF3ED`는 유지한다. 모든 패널에 같은 두꺼운 테두리를 두지 않고 경기장·선택 슬롯·실행 버튼에 강한 대비를 집중한다.
- 라임 `#D6F477`: 내 선택과 실행. 청록 `#83D9E8`: 방어·회피. 황색 `#F1CF83`: 추정 정보와 전술. 상대 표식 `#F5A58B`: 상대 식별. 글자·아이콘·실선/점선을 병행한다.
- 기본 한글은 현재 시스템 폰트 스택을 유지한다. 기술명 14~16px, 일반 설명 14px 이상, 보조 수치 12px 이상을 목표로 한다. 도트 폰트는 본문에 사용하지 않는다. 숫자는 고정 폭으로 정렬한다.
- 카드 모서리 4px, 작은 컨트롤 6px를 제안한다. 실행 버튼 끝의 사선 표식만 속도감을 강조하고 한글 본문은 기울이지 않는다.
- 경기장 높이를 실행 중에도 바꾸지 않는다. 카드 영역 역시 고정되어 다음 편집 때 손가락 위치가 유지된다.
- 390×844를 기준 화면으로 삼고 375×667·320×568에서는 세로 스크롤을 허용한다. 가로 스크롤은 만들지 않는다. 200% 글자 확대 시 카드 설명과 컨트롤이 잘리지 않아야 한다.
- 조작 목표 크기는 최소 44×44 CSS px. 8칸이 이보다 작아지는 좁은 화면은 보이는 시간축과 터치 판정을 구분하고, 선택 동작의 교체·이동·삭제는 아래 큰 컨트롤로 제공한다. 인접 터치 영역을 겹쳐서 해결하지 않는다.

## 4. 카드 선택과 편집의 리듬

아래 시간은 1차 튜닝 제안이며 게임 판정 시간이 아니다. UI 시간은 전투 속도 설정에 따라 배속하지 않는다.

| 상황 | 연출 | 시간과 입력 처리 |
| --- | --- | --- |
| 누르기 | 카드 내부가 0.97배로 짧게 눌린다. 터치 영역은 고정 | 60ms, 손을 떼면 원상 복귀 |
| 추가 성공 | 상태·기력·점유 칸을 즉시 갱신. 슬롯 안쪽에 카드색 선이 들어와 안착 | 140ms, 다음 입력은 즉시 허용 |
| 배치 선택 | 슬롯 실선과 선택 표식, 아래에 교체·삭제·이동 조작 | 80ms, 위치와 크기는 고정 |
| 교체 | 기존 내용이 빠지고 새 기술이 짧게 나타남 | 120ms, 판정용 배치는 즉시 교체 |
| 순서 이동 | 두 동작 묶음이 각각 새 위치로 이동 | 120ms, 동작의 점유 길이 유지 |
| 되돌리기 | 복원된 묶음의 테두리만 한 번 강조 | 120ms, 삭제 역재생 대기 없음 |
| 칸 부족 | 불가능 상태와 '남은 1칸 / 필요한 2칸' 안내 | 비활성 설명을 별도 읽을 수 있게 제공 |
| 실행 | 버튼 눌림, 재생 커서 등장, 편집 잠금 | 100ms 이내 첫 움직임 시작, 긴 시작 배너 없음 |

카드 원본은 목록에 남는다. 복제 이미지가 화면 전체를 날아가는 연출은 반복 선택을 방해하므로 기본안에 넣지 않는다. 배치가 이미 반영된 상태에서 짧은 효과만 따라간다. 연속 탭은 순서대로 반영하고 시각 효과를 기다리지 않는다.

키보드 Enter·Space 선택도 같은 반응을 사용한다. 카드 DOM 재생성 뒤 선택 가능한 기존 기술 버튼으로 포커스를 복원한다. 편집 잠금 중 입력은 버리고 다음 턴에 자동 실행하지 않는다.

상대 확정 정보는 실선과 '확정', 추정은 점선과 '추정', 미공개는 '?'를 유지한다. 미공개 칸은 모두 같은 크기·밝기·연출 시간을 사용한다. 숨겨진 기술이나 길이에 따라 효과를 달리하지 않는다.

## 5. 캐릭터 애니메이션

전신 이미지를 밀거나 흔들기 전에 자세 자체에서 준비·접촉·회수를 읽을 수 있어야 한다. 프레임 수는 자산 제작 목표이며 재생 FPS가 아니다. 모든 포즈는 엔진의 실제 접촉 시점에 맞춘다.

| 동작 | 필요한 구별 | 1차 고유 포즈 목표 |
| --- | --- | --- |
| 대기 | 지지발 고정, 어깨·글러브의 작은 호흡 | 4 |
| 잽 | 앞손 직선, 작은 어깨 전진, 빠른 가드 복귀 | 5 |
| 크로스 | 뒷발 피벗 → 골반·어깨 회전 → 뒷손 직선 | 6 |
| 훅 | 팔꿈치가 옆으로 열리고 가로 원호로 닫힘 | 7 |
| 바디 | 무릎으로 높이를 낮추고 몸통으로 접촉 | 6 |
| 강타 | 뒷다리 하중, 큰 체중 이동, 분명한 회수 | 7 |
| 상단·바디 가드 | 진입·유지·충격 흡수·복귀, 보호 위치 구분 | 각각 4 |
| 스웨이 | 지지발 유지, 상체 후퇴 후 복귀 | 5 |
| 위빙 | 낮아졌다 반대편으로 올라오는 하나의 U자 | 6 |
| 페이크 | 공격 준비를 닮았지만 접촉 전에 끊고 회수 | 4 |
| 머리·몸통 피격 | 머리는 뒤로, 몸통은 접히는 다른 반응 | 각각 4 |
| 호흡·다운 | 호흡은 작은 움직임, 다운은 균형 상실 후 착지 | 4 / 7 |

각 프레임에 발 기준점과 머리·몸통·앞/뒷글러브 접촉점을 기록한다. 공중에 뜨지 않는 동작에서 발이 위아래로 흔들리지 않게 한다. 아틀라스는 투명 배경, 같은 인물·비례·광원, 여유 있는 소스 사각형을 유지한다.

연속 잽→크로스, 위빙→훅은 매번 완전한 대기 자세를 끼우지 않는다. 이전 회수의 자세를 다음 준비와 연결하되 공격 준비·판정 시점·가드 활성 구간을 앞당기지 않는다. 새로운 자산 제작은 두 선수 모두 같은 동작 목록으로 진행한다.

## 6. 전투 효과와 음향

| 사건 | 화면 | 제안 시간 |
| --- | --- | --- |
| 일반 명중 | 접촉점의 작은 밝은 타격형 + 해당 부위 반응 | 70~100ms, 화면 흔들림 없음 |
| 블록 | 글러브·팔 접촉점의 청록 압축선, 짧은 둔탁음 | 80ms |
| 회피 | 공격 궤적의 짧은 잔상과 회피 표식 | 100ms, 명중 섬광 없음 |
| 강타 | 접촉점 확장, 경기장만 최대 2 CSS px 흔들림 | 정지 30ms, 효과 120ms |
| 카운터 | 밝은 접촉선과 '카운터' 한 번, 낮은 타격음 | 정지 45ms, 표식 280ms |
| KO | 균형 상실→착지→경기 결과 | 약 450ms의 쓰러짐 시퀀스 |

정지 시간은 배속과 별개인 실제 시간으로 제안한다. 겹친 명중은 가장 강한 정지 하나만 적용하고 한 콤보의 누적 정지는 120ms로 제한한다. 이는 현재 구현에서 변경할 표시 정책이며 실제 체감 검증 후 조정한다. 일반 명중에 정지를 반복해서 넣지 않는다.

효과·음향은 엔진 이벤트에서만 발생한다. 동시에 두 선수가 맞으면 두 접촉점을 각각 표시하며 카메라 정지와 음향은 중첩을 제한한다. 기력 부족은 힘없는 회수와 짧은 사유를 보여주고 성공 타격 효과는 내지 않는다.

마지막 사건 후 160ms 이내 다음 계획을 편집할 수 있게 한다. 결과 요약은 '카운터 1회 · 몸통 피격 1회'처럼 실제 사건만 짧게 남기며 자동 복귀를 막지 않는다. KO는 다음 콤보 편집 대신 경기 결과로 간다.

소리는 기존 기본 꺼짐을 유지한다. 선택은 짧은 클릭, 배치는 낮은 틱, 공격은 바람음과 접촉음의 조합으로 구별한다. UI 효과음을 빠른 연타마다 겹쳐 쌓지 않는다. 음향 자산이 추가되면 직접 제작하거나 사용 조건을 확인한 파일을 쓴다.

동작 줄이기에서는 카드 이동·축소, 잔상, 흔들림, 줌, 정지 효과를 끈다. 기술 포즈와 결과 표식은 남기며 읽기 시간은 줄이지 않는다. 전체 화면 흰색 번쩍임은 사용하지 않는다.

## 7. 구현 순서와 범위

1. **최소 적용: 카드 반응과 실행 연결.** `dist/style.css`, `dist/app.js`, 필요 시 `dist/index.html`을 수정한다. CSS로 색·레이아웃을 관리하고 이동 효과는 브라우저 기본 Web Animations API를 사용한다. 같은 속성을 CSS 애니메이션과 중복 제어하지 않는다. 새 프레임워크·계정·외부 서비스는 필요 없다.
2. **전투 효과 정리.** `dist/motion.js`, `dist/ring-pixel.js`에서 사건당 한 번 발생하는 효과·정지 예산·재생 종료 연결을 구현한다. 정지·스킵·다시 보기에도 이미 계산한 결과를 유지한다. 기존 아틀라스로 독립 적용 가능하다.
3. **고유 동작 자산.** 먼저 잽·크로스·훅·피격을 두 선수 모두 제작·비교하고, 나머지 표의 동작까지 확장한다. `dist/pixel-motion.js`와 자산 파일에 프레임·기준점을 등록한다. 각 묶음은 기존 동작을 유지하며 독립 교체한다.

전체 구현은 자산·테스트를 포함해 8개 이상의 파일에 걸칠 가능성이 크다. 1단계는 작음, 2단계는 중간, 3단계는 가장 큰 작업이다. 가장 불확실한 비용은 동일 인물과 발 위치를 유지하는 연속 스프라이트 제작이다. 현재 그림을 단순 보간하는 것만으로 이 단계를 완료했다고 하지 않는다.

엔진 판정·카드 비용·점유 길이·상대 정보 생성·세이브 형식은 이 연출 작업의 변경 대상이 아니다. 기존 입력과 관찰 상태를 받아 표시하는 단방향 구조를 유지한다.

## 8. Blender 제작 경로와 도구 — 이전 제안, 채택 보류

사용자가 이번 작업에서 Blender MCP를 추가했다고 알렸다. 2026-09-12 연결 문제를 조사해 Windows loopback에 열린 애드온으로 WSL gateway를 통해 접속하던 주소 불일치를 확인했다. 전역 MCP 실행을 Windows 전용 환경으로 바꾼 뒤 실제 저장 설정을 이용한 MCP 도구 25개 조회와 `get_scene_info` 호출이 성공했다. Blender 5.2.0 LTS·addon protocol 4와 Cube/Light/Camera 장면을 확인했다. 현재 Codex 작업 도구 목록의 재로딩은 별도 확인 대상이다. 제작 기능 전체나 모델·애니메이션 품질을 검증한 것은 아니다. 연결 방법과 증거는 공용 `game-tools/README.md`에 기록했다.

권장 제작 경로는 Blender의 리깅된 선수로 준비·접촉·회수와 체중 이동을 만들고, 고정 측면 카메라·조명·출력 크기에서 투명 PNG 프레임을 렌더하여 현재 Canvas 아틀라스로 연결하는 것이다. 게임 런타임의 3D 전환을 뜻하지 않는다. 작은 출력 크기만으로 현재 도트 그림과 같은 결과가 보장되지는 않으므로 가장자리·색면·헤어 표현을 비교하고 픽셀 정리 여부를 결정한다.

먼저 두 선수의 리깅 가능한 모델 보유 여부와 MCP의 장면 조회·스크립트 실행·렌더 지원을 확인한다. 모델이 없다면 기본 리그로 잽·크로스·훅의 동작 검토까지만 진행하고, 그 임시 형상을 최종 외형으로 채택하지 않는다. 외형 제작 단계는 지정된 링크 이미지와 나란히 비교한다.

추가 다운로드는 현재 필수가 아니다. 도트 프레임의 수작업 정리가 필요해지면 전용 픽셀 편집기를 검토하고, 애니메이션 승인 증거는 프레임별 캡처와 정상 속도 영상으로 남긴다. 도구 추가 전에 기존 Blender·브라우저·이미지 처리 기능으로 작은 샘플을 완성해 실제 부족한 기능을 확인한다.

## 9. 검증과 완료 기준

- WSL 저장소 루트에서 `npm test`, `git diff --check`를 실행한다. 현재 문서 작성만으로 런타임 통과를 주장하지 않는다.
- `ui-flow.test.mjs`: 빠른 연속 선택, 교체·되돌리기 후 포커스, 실행 중 편집 차단, 자동 복귀를 확인한다.
- `motion.test.mjs`: 1·2·3배, 긴 프레임 지연, 동시 타격, 스킵·재생·일시정지 후 중복 효과 방지, 정지 예산과 결과 불변을 확인한다.
- 아틀라스 범위와 기준점 테스트를 보강하되 화면 비교를 대신하지 않는다. 모든 공격은 준비·접촉·회수 캡처를 남긴다.
- Chrome에서 390×844, 375×667, 320×568, 1440×900과 글자 200%를 검증한다. 실제 휴대폰의 성능 검증은 별도 수행한다.
- 기본 2배의 보통 8칸 교환은 약 3.0~3.3초를 목표로 한다. KO·수동 일시정지는 제외한다. 입력의 상태 반응은 다음 표시 프레임을 목표로 하고 시각 효과 완료를 기다리지 않는다.
- 연속 10회 카드 입력의 순서·수량이 맞고, 잘못된 추가 입력이나 다음 턴 자동 입력이 없어야 한다.
- 기술명 없이도 잽·크로스·훅과 상단/바디 가드를 구분할 수 있는지 캡처와 정상 속도 영상으로 평가한다.
- 숨겨진 계획이 다른 두 상태라도 허용된 관찰 정보가 같으면 계획 화면·효과·플레이어 로그가 같아야 한다.
- 동작 줄이기·소리 꺼짐·좁은 화면에서도 성공/실패/확정/추정을 읽을 수 있어야 한다.

각 단계는 변경 파일과 자산만 되돌려 복구한다. 데이터 마이그레이션은 없다. 이 문서는 설계 결과이며 구현·브라우저 검증·출시 완료를 의미하지 않는다.
