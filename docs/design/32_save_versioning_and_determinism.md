# FCM Delegated Design 32 — 세이브, 버저닝, 재현성

> 상태: 수치와 형식 세부는 구현 언어 결정 시 확정한다.
> 기준: [개념 데이터 모델](../spec/data_model_part1_part2.md) 2·39·41장, [구현 로드맵](../spec/implementation_roadmap_part1_part2.md) Phase 0
> 실물 Config: `config/save.json`
> 범위: 로드맵 Phase 0의 미명세 구간. 저장 대상, 버전 정책, 재현 보장.

## 해결하는 문제

`GameState`에 `save_version`과 `config_version` 필드는 있지만 **무엇을 저장하고 무엇을 저장하지 않는지,
버전이 어긋나면 어떻게 하는지**에 대한 규칙이 없었다.

Phase 0의 완료 기준은 "같은 Seed + 같은 입력으로 같은 결과 재현"인데, 이를 보장하는 조건도 정의되지 않았다.

---

# 1. 저장하는 것과 저장하지 않는 것

`data_model` 39장의 Definition / Runtime 분리를 저장 형식에 그대로 적용한다.

| 구분 | 저장 | 이유 |
|---|---|---|
| Runtime State | **O** | 세이브마다 달라지는 실제 진행 |
| Definition Data | **X** | 콘텐츠·밸런스. `config_version`만 기록 |
| Derived Capability | **X** | 계산 결과다 |
| Effective Performance | **X** | 캐시다. 한 칸 수명이다 |
| Knowledge State | **O** | True State와 **별도로** 저장 |

## Derived를 저장하지 않는 이유

Derived를 저장하면 Config를 수정했을 때 저장된 값과 계산값이 어긋난다.
밸런스 패치가 기존 세이브에 반영되지 않거나, 일부만 반영되어 설명 불가능한 상태가 된다.

**계산 가능한 것은 저장하지 않는다.** 로드 시 Definition Data로 다시 만든다.

---

# 2. 두 개의 버전

| 버전 | 대상 | 불일치 시 |
|---|---|---|
| `save_version` | 세이브 **스키마** 구조 | 전진 마이그레이션 체인을 실행 |
| `config_version` | 밸런스·콘텐츠 **데이터** | 로드는 허용하고 경고한다 |

## 왜 정책이 다른가

스키마가 바뀌면 데이터를 읽을 수 없으므로 변환이 **필수**다.
밸런스가 바뀌면 데이터는 여전히 읽히고, 값이 달라지는 것은 **정상**이다.
패치 후 기존 세이브의 선수 능력이 조금 달라지는 것은 버그가 아니다.

마이그레이션은 한 단계씩 누적 적용한다. `v1 → v2 → v3`이며 `v1 → v3` 직행 경로를 따로 만들지 않는다.
경로가 하나뿐이어야 테스트할 수 있다.

## 참조 무결성

Config에서 Technique이나 Skill Card가 **삭제되면** 세이브가 없는 ID를 가리킨다.

- 로드 시 모든 참조를 검증한다
- 끊어진 참조는 조용히 무시하지 않고 기록한다
- 선수가 보유한 삭제된 콘텐츠는 제거하되 이벤트 히스토리에는 남긴다

콘텐츠 삭제보다 **비활성화(deprecated)** 를 기본으로 한다. 삭제는 최후 수단이다.

---

# 3. 재현성 — Seed만으로는 부족하다

`rng_seed`만 저장하면 재현되지 않는다. **얼마나 소비했는지**를 함께 저장해야 한다.

- 스트림별 소비 카운터를 저장한다
- RNG 스트림을 용도별로 분리한다: 월드 생성, NPC 시뮬레이션, 전투, 부상, 이벤트
- 스트림이 분리되어 있으면 한 시스템의 호출 횟수 변경이 다른 시스템의 결과를 흔들지 않는다

스트림 분리는 재현성만이 아니라 **개발 중 밸런스 비교**를 위해 필요하다.
전투 코드를 수정했는데 월드 생성 결과까지 바뀌면 A/B 비교가 불가능하다.

---

# 4. 전투 중 저장

**전투 상태 전체를 저장하지 않는다.**

전투는 26번에 따라 완전히 결정론적이므로 다음만 저장하면 복원된다.

```text
전투 시작 스냅샷 + 확정된 ComboPlan 시퀀스 + 전투 RNG 스트림 상태
```

로드 시 그 계획들을 다시 실행해 현재 시점까지 재생한다.

이 방식의 이점이 크다.

- 세이브 크기가 작다
- **리플레이 기능과 같은 메커니즘을 쓴다.** 별도 코드가 필요 없다
- 재현되지 않으면 그 자체로 결정론이 깨졌다는 신호다. 세이브가 회귀 테스트가 된다

---

# 5. Event History 성장 관리

모든 중요한 변화를 이벤트로 남기면(`data_model` 38장) 10년 진행 후 무한히 커진다.

압축 정책:

- 최근 구간은 전체 보존
- 오래된 구간은 Simulation Tier에 따라 축약. Tier C 배경 세계 이벤트는 요약으로 대체
- **Evidence의 출처가 된 이벤트는 축약하지 않는다.** 축약하면 재해석이 불가능해진다
- 플레이어 관련 이벤트(계약, 타이틀, 부상, Breakthrough)는 영구 보존

29번이 "더 좋은 해석자로 과거 Evidence를 재분석"을 허용하므로,
Evidence 출처 이벤트의 보존은 게임 기능의 전제다.

---

# 6. 저장 단위

기본 시간 단위가 Week이므로 주 경계를 기본 저장 지점으로 둔다.
전투 중 저장은 4장의 방식으로 처리한다.

자동 저장은 주 경계에서 순환 슬롯에 기록한다. 수동 저장 슬롯과 분리한다.

---

# 7. 미결 항목

- 직렬화 형식. 구현 언어 결정 후 확정
- 압축 여부와 세이브 크기 목표
- 자동 저장 슬롯 개수와 순환 정책
- 이벤트 축약의 구체 임계와 요약 형식
- 마이그레이션 실패 시 처리. 거부할지 부분 복구할지
- 클라우드 세이브 및 다중 프로필 지원 여부
- 세이브 무결성 검증 수준. 체크섬 도입 여부

---

# 8. 검증 기준

- 저장 후 즉시 로드하면 모든 관찰 가능한 상태가 동일하다
- 세이브에 Derived나 Effective 값이 포함되지 않는다
- Config 값을 바꾸고 로드하면 능력치가 새 Config로 다시 계산된다
- `config_version`이 달라도 로드되며 경고가 기록된다
- `save_version`이 낮으면 마이그레이션 체인이 순서대로 적용된다
- 삭제된 Definition을 가리키는 참조가 로드 시 검출되어 기록된다
- 전투 중 저장 후 로드하면 같은 시점까지 동일하게 재생된다
- RNG 스트림을 분리한 상태에서 전투 코드를 수정해도 월드 생성 결과가 바뀌지 않는다
- Evidence의 출처 이벤트가 히스토리 압축으로 소실되지 않는다
- 같은 세이브와 같은 Config로 Headless 실행 시 결과가 완전히 동일하다
